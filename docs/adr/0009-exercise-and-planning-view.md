# ADR 0009: Exercise phases, plan revisions and the 2D planning view

- Status: Accepted; the phase model is extended by ADR 0010
- Date: 2026-10-07

## Context

Phase 3 is the first interactive slice: the trainee plans routes for BLUEFOR
soldiers on a 2D map, executes, pauses, re-plans and resumes. ADR 0004
separates plan state (exercise) from simulation state and session/UI state;
this ADR makes that separation concrete.

## Decision

### Exercise phases

`Planning → Executing ⇄ Paused`, owned by the `exercise` layer (no DOM).
ADR 0010 refines this into the ambush sequence (BLUEFOR Planning → Occupation
⇄ paused → Ready → OPFOR Approach → Ambush Triggered); the rules below still
apply to BLUEFOR Occupation.

- The exercise owns the simulation and the fixed-step runner. `advance(realDt,
timeScale)` steps the simulation only while Executing, so it is frozen while
  Planning and Paused.
- `advance` steps whole ticks, so Pause always lands on a tick boundary. Any
  fraction of a tick accumulated before Pause is discarded on Resume.
- The time scale (1×, 2×, 4×) is session state, passed to `advance` each frame.
  The simulation never sees it.
- Ended/Review are not built yet.

### Draft plans and plan revisions

A `SoldierPlan` is `{ soldierId, waypoints: { id, x, y }[], finalFacing }`, the
same shape for drafts and committed plans. Only the trainee side (BLUEFOR) has
drafts.

- **Drafts** are editable only while Planning or Paused, through
  `addWaypoint`/`moveWaypoint`/`deleteWaypoint`/`clearRoute`/`setFinalFacing`.
  Edits outside the rules (wrong phase, OPFOR, point off the map) throw an
  `ExerciseError`. The simulation never sees a draft.
- **On Pause**, each draft is reset to what the soldier still has to do: the
  waypoints not yet reached (keeping their ids) and the final facing. The
  trainee edits the remaining route from the soldier's current position and
  never rebuilds completed legs.
- **On Execute/Resume**, every draft is validated (waypoints on the map, unique
  ids, a valid facing). If any draft is invalid, nothing is committed and the
  problems are returned. Otherwise an immutable (deep-frozen) `PlanRevision` is
  recorded: revision number, trigger, tick, time, every trainee soldier's plan,
  and which soldiers changed. `setOrders` is submitted only for soldiers whose
  plan differs from what they are already doing, stamped with the current tick.
  Unchanged soldiers continue undisturbed; a test checks that pause → resume
  without edits leaves the simulation bit-identical to an uninterrupted run.
- "What the soldier is already doing" is the remaining active orders, except
  between a commit and the next tick, when it is the just-committed plan (its
  orders are queued but not yet applied). This keeps the display and a quick
  Pause → edit → Resume consistent.
- Revisions are kept in memory for the future AAR. Recording comes in Phase 6.

### Waypoint identity

Waypoint ids are generated by the exercise as `<soldierId>.<n>`, with a
per-soldier counter that is never reset or reused. A waypoint keeps its id
when it is moved. Remaining waypoints keep their ids across pauses and
revisions.

For the AAR this means:

- the same id across revisions is the same trainee intent, possibly moved;
- a new id is a new waypoint;
- `waypointReached` events (ADR 0008) carry the id, so planned and actual
  arrivals can be matched.

The map numbers waypoints by their position in the route, which is what the
trainee needs for ordering.

### 2D tactical view

- **Canvas 2D**, no rendering or UI framework. The UI shell is plain DOM.
- **Camera** (`view2d/camera.ts`): pure functions between screen pixels and map
  East/North metres, with equal scale on both axes, north always up and no
  rotation. Zoom keeps the point under the cursor fixed. Pan moves the map
  with the pointer. Fit shows the whole terrain.
- **Terrain imagery** is computed once: a hypsometric tint with north-west
  hillshade (one pixel per sample, smoothed), and 2 m contours with 10 m index
  contours. Contours are traced on the simulation's terrain triangles
  (ADR 0008), so they match `heightAt` exactly.
- **Symbols**: BLUEFOR blue circles, OPFOR red diamonds (echoing, not
  implementing, MIL-STD-2525/APP-6 frames), a facing tick, a yellow ring for the
  selection. The selected route has numbered waypoints and direction chevrons.
  Other planned BLUEFOR routes are faint and dashed. While Executing, the route
  is dashed and shows only what remains.
- **Interaction** (`view2d/interaction.ts`) is a DOM-free state machine over
  pointer input. It calls `MapActions`, wired to the exercise and session in
  `view2d/actions.ts`. Tests drive it with synthetic input against a real
  exercise.
- **Selection** is session state; only trainee soldiers can be selected.

### Demo scenario

`DEMO_SCENARIO` (exported from `#exercise`) is development content: a BLUEFOR
rifle squad (squad leader and two four-soldier fire teams), a three-soldier
stationary OPFOR team, and 800 m × 600 m of synthetic terrain.

## Consequences

- A future 3D view can reuse the exercise, session and plan model unchanged.
- The AAR (Phase 6) can relate plan revisions and executed events through
  waypoint ids and revision ticks.
- Multi-selection, undo and group (fire-team) planning are not supported yet.
